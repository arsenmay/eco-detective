# Аудит исходной ECO DETECTIVE 2.0 и решения для версии 3.0

Дата аудита: 10 октября 2026 года. Исходный снимок: `d9281e7` («Document ECO DETECTIVE 2.0 campaign and verified deployment»), приложение `2.0.0`. Документ описывает исходное состояние **до** модернизации; наличие функции в предлагаемой архитектуре не означает, что она уже реализована.

Работа продолжается в существующем проекте TypeScript / Phaser 3 / Vite. Сюжетная кампания, существующие расчёты, мобильное управление, сохранения и тесты являются обязательной регрессионной базой. Ветку разработки и фиксацию фаз ведёт основной исполнитель; этот аудит не изменяет игровую логику.

| Прогресс | Разблокировка следующего дела, уникальные награды, XP, семь званий, девять достижений | Нет отдельного прогресса процедурных задач, 3D-точек, помощника или домашней практики |

| Сохранения | Кампания v2, перенос старого v1, независимые позиции дел, проверка данных, recovery-копия повреждений, сообщения об отказе хранилища | Нормализатор пересоздаёт объект и удаляет незнакомые поля; простое добавление данных 3.0 в объект v2 не обеспечит сохранность |

## 3. Решение для 2.5D

Выбрана отдельная проекция визуального мира при сохранении логической 2D-геометрии. Это позволяет не переписывать пять наборов препятствий, старые координаты сохранений и проверенные алгоритмы взаимодействия.

Проекция должна быть чистым модулем с `worldToScreen`, `screenToWorld`, `getDepth` и `getObjectBounds`. Общий вид аффинного преобразования:

```text
screenX = originX + a × worldX + b × worldY
screenY = originY + c × worldX + d × worldY − elevation
det = a × d − b × c ≠ 0
```

Обратное преобразование для поверхности пола использует обратную матрицу. Высота отделена от пола: нельзя превращать верхнюю грань стола в позицию тела игрока. Коэффициенты, начало координат и высота мебели задаются в одном месте, а не независимо в каждом renderer.

Arcade-физика остаётся в логическом пространстве. Видимая фигура игрока, тень, мебель и маркеры используют одну проекцию. Столкновение проверяется по основанию мебели, а не по экранному прямоугольнику с высотой. Точка взаимодействия связана с физическим оборудованием, а не с отдельно нарисованной картинкой.

Глубина вычисляется от экранной координаты опорного основания: нижняя точка мебельного footprint определяет порядок перекрытия. Пол и общие тени имеют нижние слои, стены с высотой имеют управляемую прозрачность при перекрытии игрока, подписи интерфейса располагаются отдельно от предметной глубины. Статическую мебель нельзя запечь целиком вместе с полом, если её передняя грань должна перекрывать персонажа.

Камера следует за **проецируемым визуальным якорем**, а сохранение продолжает получать логическую позицию. Границы камеры вычисляются из всех проецируемых углов помещения с учётом высоты стен и отступов. Изменение размеров окна не меняет положение физического тела. Экранный вектор джойстика/клавиатуры преобразуется согласованно; ограничение диагональной скорости проверяется отдельно.

Сначала завершается кабинет информатики, затем тот же renderer и правила глубины применяются к другим четырём планировкам. Старые процедурные artwork-модули остаются источниками деталей/палитр и возможного упрощённого режима, но не смешиваются с 2.5D в одной активной комнате.

## 4. Зависимости и настоящий 3D-осмотр

Исходная runtime-зависимость одна: **Phaser 3.90.0**. Vite 7.1, TypeScript 5.9, tsx, vite-plugin-pwa и типы Node используются для разработки и сборки. `createRoom` выбирает `Phaser.CANVAS`, поэтому сама игровая сцена работает без WebGL. Этот выбор полезно сохранить для доступности и независимого fallback.

Настоящий 3D создаётся отдельным модулем Three.js, загружаемым через `import()` только после открытия осмотра. Three.js — обоснованная дополнительная runtime-зависимость; `@types/three` требуется как devDependency, если выбранная версия не содержит собственных деклараций. Версии фиксируются lockfile, модели создаются локально из low-poly геометрии. Для такого объёма не требуется второй игровой движок, платный сервис или загрузчик внешних тяжёлых сцен.

Рекомендуемый контракт модуля:

```ts
type InspectorHandle = { dispose(): void };
// createInspector(host, equipment, quality, onPointSelected) -> InspectorHandle
```

Первый вертикальный сценарий: открыть системный блок → вращать мышью и пальцем → выбрать реальную mesh-точку → прочитать её сведения → изменить масштаб → вернуть ракурс → закрыть. После его проверки добавляются остальные категории, а не набор декоративных пустых вкладок.

Модуль ограничивает DPR и дальность камеры, использует немного материалов и света, не выполняет RAF после закрытия/скрытия страницы. `dispose()` снимает controls, ResizeObserver, DOM/event listeners, отменяет RAF и освобождает геометрию, материалы, renderer. При отсутствии WebGL, ошибке загрузки или context loss показывается содержательный 2D-осмотр того же устройства. Асинхронный import проверяет актуальность открытой панели, чтобы не создать canvas после закрытия.

Workbox сейчас precache-ит все JS. Динамический import откладывает выполнение и создание WebGL, но precache может скачать chunk в фоне ради offline. Это необходимо явно различать при оценке начальной нагрузки. Офлайн-тест должен подтвердить, что осмотр работает после первого полного кеширования; корректность проверяется и для `/`, и для `/eco-detective/`.

## 5. Энергосистема без двойного учёта

Существующие демонстрационные месячные электрические балансы: кабинет **151,88**, холл **73,44**, кухня **470,4**, школа **705,32 кВт·ч** за 20 выбранных учебных суток. Тепловая модель отдельно: **262,912 кВт·ч тепла**. Эти значения проверены тестами и не являются измерением.

Общий реестр нельзя строить суммированием всех 39 источников. Дело 005 содержит сводные группы уже рассмотренных помещений, а документы, окна и тепловые показания — источники данных, не дополнительные электрические нагрузки. Начальный реестр использует физические электрические устройства дел 001–003 плюс уникальную критическую серверную нагрузку из финала. Окна/дверь дела 004 образуют отдельный тепловой контур.

Для каждого устройства нужны уникальный ID, roomId, количество, мощности взаимоисключающих состояний, непересекающиеся интервалы, safety/dependency-ограничения. На одном интервале устройство находится в одном режиме: active и standby не суммируются за одни и те же часы. Модель потребления интегрирует мощность по времени; тепловые потери остаются отдельным показателем. Любой динамический event меняет конкретный входной параметр модели и проверяемый результат, а не только текст.

`SchoolEnergySimulator` рекомендуется сделать чистым модулем данных и расчётов. DOM-графики и состояние renderer подписываются на вычисленные результаты; симулятор не обращается к Phaser. Изменения в исследовательской лаборатории не должны автоматически переписывать утверждённые сюжетные планы или начислять XP. Условия сюжетного завершения остаются в `submitCampaignPlan`.

Исходный `puzzles.ts` содержит явные baseline-константы, стоимости и пороги пяти дел. Это подходящий источник стабильной сюжетной проверки, но плохо подходит для изменяемых пользователем мощностей. Новая лаборатория, генератор и «Моя школа» используют общий расчётный API с отдельными схемами, не подставляют пользовательский scenario в старую функцию с фиксированными числами.

## 6. Совместимость сохранений

Исходные ключи:

- `eco-detective:progress:v1` — первая версия, сохраняется для миграции и восстановления;
- `eco-detective:campaign:v2` — каноническая пятиуровневая кампания;
- `eco-detective:campaign:v2:recovery` — необработанный повреждённый payload перед безопасной заменой;
- `eco-detective:settings:v1` — проверенные настройки и чувствительность.

`normalizeCampaignSave()` проверяет версии, ID, значения, позиции, этапы и планы, пересобирает все пять записей и сверяет уникальные награды. Неизвестные свойства теряются при сохранении. Поэтому **не добавлять несогласованное поле `v3Data` к объекту v2** и не менять version с 2 на 3 без полноценной миграции.

Для первого обновления безопаснее отдельный версионированный ключ расширений 3.0: проверенные связи доски, уровни помощи, исследованные 3D-точки, seed дополнительных дел, параметры лаборатории, домашний самоотчёт и пользовательские сценарии. Его схема имеет собственный version, границы строк/массивов/чисел и обрабатывает повреждение независимо от рабочей кампании. Повреждение дополнительного режима не должно удалять завершённые дела и XP.

Сюжетные ID и логические координаты v2 остаются прежними. Новые обязательные механики не лишают старую completed-запись завершения: доска может быть дополнительной тренировкой либо обязательной только для нового незавершённого этапа с явным grandfather-правилом. Запись расширения не должна создавать неизвестные reward IDs внутри канонической кампании.

Режим «Моя школа» имеет отдельную схему JSON с происхождением показателей: демонстрационные данные / ввод пользователя / самоотчёт измерений. Импорт проходит runtime-валидацию, ограничения размера, типов, мощности, количества и часов; строковые названия экранируются при рендеринге. Импорт пользовательского scenario не даёт доступа к locked case и не превращает пользовательские числа в измерения СШ №225.

## 7. Модули новых режимов

Предлагаемые самостоятельные seam-модули (названия могут быть согласованы при реализации):

- `game/projection.ts` — чистая математика проекции, глубина и bounds;
- `game/projectedArtwork.ts` — visual world/quality с логическими footprint;
- `inspection/EquipmentInspector.ts` — lazy Three.js и корректный lifecycle;
- `systems/evidenceBoard.ts` — допустимые связи, необходимые источники, проверка цепочек;
- `systems/wattAssistant.ts` — локальные три уровня помощи по этапу/уликам, без API;
- `systems/schoolEnergy.ts` — виртуальное время, состояния, расписания, баланс и последствия;
- `systems/generatedCases.ts` — seed, решение сначала, затем улики/ложные следы, проверка разрешимости;
- `systems/scenarioEditor.ts` — пользовательские устройства, вычисления, проверка JSON;
- `systems/v3Storage.ts` — независимая проверка и сохранение расширений;
- `ui/*Panels.ts` — UI школы, доски, помощника, энергосистемы, лаборатории, редактора и практики.

Генератор лучше строит безопасное решение и ограничения **до** случайного оформления задачи, затем вычисляет все показатели и проверяет, что решение достижимо. Один seed и сложность воспроизводят одни исходные данные. Новые режимы не смешивают события, игровые кредиты, XP и физические единицы в одну сумму.

Центральный холл реализуется как отдельная небольшая игровая зона с доступными дверями и переходом в уже существующий caseId, а не как шесть одновременно загруженных сцен. Карта остаётся быстрым путём. Условия открытия берутся из `isCaseUnlocked`; свободное исследование доступно лишь для открытых помещений и не меняет сюжетные этапы.

## 8. Основные риски и способ проверки

| Риск | Проверка / ограничение |
| --- | --- |
| Визуальный предмет и физическое тело разошлись | Round-trip проекции; общие anchors; движение и взаимодействие у каждого из 39 источников |
| Мебель всегда поверх игрока | Проверка depth перед/за столом и шкафом; мебель отдельным объектом; screenshot-сценарии |
| Камера показывает пустоту после проекции/resize | Bounds из проекции; повторные portrait/landscape/zoom/resize; позиция save не меняется |
| Джойстик двигает по неправильному экранному направлению | Проекция экранного вектора; цифровая диагональ и аналоговый масштаб; мультитач и pause/blur |
